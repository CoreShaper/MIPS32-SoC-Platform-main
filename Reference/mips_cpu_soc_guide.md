# MIPS CPU SoC 工程说明

## 1. 工程概述

本工程实现了一个可运行的 MIPS CPU-SoC 基础系统，已经形成从软件编译、镜像生成、RTL 仿真到异常/中断处理与调试输出的完整闭环。工程以硬件系统构建为主线，在此基础上补齐了必要的软件运行支持与仿真平台能力，可用于展示一个基础 SoC 系统从处理器、存储、控制到验证运行的完整实现过程。

当前版本的核心并不在于复杂总线或大量外设，而是在可控范围内完成了一个基础 SoC 所需的关键能力：处理器执行、统一存储组织、异常与中断支持、仿真结束控制、调试输出以及可重复运行的仿真平台。对于数字 IC / RTL / SoC 方向的项目展示而言，这一版本更强调“系统已经跑起来”，并且具备软硬件协同运行与验证能力。

当前工程已经具备以下完整能力：

- 基于 MIPS CPU 核构建基础 SoC 系统
- 建立交叉编译、链接、镜像生成与仿真运行链路
- 支持异常与中断的进入、分发与返回
- 通过 MMIO 建立仿真结束控制与调试输出机制
- 通过 testbench 形成可观察、可判断、可调试的仿真闭环

从项目定位看，这不是单独的 CPU 核展示，也不是单一的测试用例集合，而是一个已经具备基本系统组织能力的 CPU-SoC 工程版本。

## 2. 系统总体架构

当前系统围绕“CPU 核心 + 存储系统 + MMIO 控制 + 仿真平台”构成一个最小可运行 SoC。其目标不是在现阶段追求复杂互联，而是先形成一个能够实际执行软件、响应异常/中断并支持调试输出的系统闭环。

系统可以概括为以下结构：

```text
CPU 核心
├── 指令执行与控制通路
├── CP0 异常 / 中断支持
└── 指令 / 数据访问接口

存储系统
└── 双口 RAM（指令端口 + 数据端口）

MMIO 与仿真控制
├── 仿真结束控制
└── 调试输出

仿真平台
├── 程序加载
├── 时钟 / 复位驱动
└── 结果观测
```

在这一结构下，CPU 负责完成指令执行、访存控制以及异常/中断处理；双口 RAM 同时承担程序存储与数据访问；MMIO 控制用于向仿真环境传递结束状态和调试信息；testbench 负责驱动系统运行并观察结果。

从运行流程看，整个工程已经形成清晰的闭环：

1. 软件源程序经过交叉编译与链接生成目标镜像  
2. 仿真平台加载镜像到存储系统  
3. CPU 从复位开始执行程序  
4. 程序在运行过程中完成访存、异常/中断处理与调试输出  
5. 仿真平台根据控制寄存器和输出信息判断运行状态  

因此，当前系统不是零散模块的拼接，而是一个具备完整运行路径和基本可验证能力的 SoC 原型。

## 3. 硬件系统设计

### 3.1 SoC 顶层组成

当前 SoC 顶层主要由以下几部分组成：

- MIPS CPU 核心
- 双口 RAM 存储系统
- MMIO 仿真控制寄存器
- 调试输出寄存器
- 中断接入逻辑
- SoC 顶层封装与 testbench 接口

从工程角度看，这样的结构已经覆盖了基础 SoC 的核心组成：计算核心、存储系统、控制路径和验证观测路径。虽然当前版本的外设数量不多，但系统结构已经完整，具备继续扩展的基础。

### 3.2 CPU 核心与控制能力

CPU 是整个系统的执行中心，负责完成指令执行、分支跳转、访存控制以及异常/中断响应。当前工程中的 CPU 不仅能够运行普通程序，还已经具备系统级控制能力，能够支持异常入口、异常返回和中断处理等基础控制流。

对于一个 CPU-SoC 工程而言，这一点非常关键。只有当 CPU 不再停留于“能执行几条指令”的层面，而是能够承担系统启动、控制转移、异常响应和外设控制等职责时，才真正具备了作为控制核使用的条件。

### 3.3 双口 RAM 与存储组织

当前系统采用双口 RAM 作为统一存储基础，其中一个端口服务于取指访问，另一个端口服务于数据访问。这样的组织方式符合当前阶段的工程目标：在不引入更复杂总线仲裁结构的前提下，快速完成程序运行闭环。

这种设计有几个直接好处：

- 存储结构简单，便于系统 bring-up
- 可以清晰地区分取指访问与数据访问
- 便于软件镜像直接加载到系统中运行
- 有利于与仿真平台结合，快速验证 CPU-SoC 行为

当前版本下，双口 RAM 既承担程序代码的存放，也承担软件运行期间的数据读写，是整个系统最基础的共享资源。

### 3.4 MMIO 与仿真控制机制

为了便于在仿真环境下观测程序执行结果，当前系统在 MMIO 空间中定义了专门的仿真控制接口，用于实现两类功能：

- 向 testbench 传递程序执行结果
- 向 testbench 传递调试输出字符

这使得程序运行结束后可以主动通知仿真平台 PASS/FAIL，也可以在执行过程中输出调试信息，从而降低对纯波形观察的依赖，提升系统调试效率。

当前工程中的关键地址约定如下：

| 地址 | 用途 | 说明 |
|---|---|---|
| `0xFFFFFFF0` | 仿真结束控制 | 程序写入后，仿真平台可据此判断执行结果 |
| `0xFFFFFFE0` | 调试输出 | 程序写入字符后，仿真平台将其打印到控制台 |

通过这种 MMIO 机制，当前系统具备了“可结束、可输出、可调试”的仿真交互能力。

### 3.5 当前硬件结构小结

从硬件角度看，当前版本已经完成了一个基础 SoC 所需的关键构件：

- 有处理器核心
- 有统一存储系统
- 有控制与观测接口
- 有异常/中断支持
- 有可运行的顶层封装

因此，这一版本的价值不在于外设数量，而在于已经建立起一个真实可运行的 CPU-SoC 结构。

## 4. 软件与运行支持

### 4.1 软件链路概述

虽然本工程以硬件系统为主，但当前版本已经建立了完整的软件运行支持链路。软件部分的作用并不是扩展复杂应用，而是为 SoC 提供必要的启动、异常处理、测试程序和调试支持，使整个系统真正能够运行起来。

整体流程可以概括为：

```text
C / 汇编源程序
→ 交叉编译
→ 链接生成 ELF
→ 转换为镜像文件
→ 仿真平台加载
→ CPU 执行
```

这一流程体现出当前项目不仅完成了硬件 RTL 设计，也已经建立了配套的软件底层运行环境。

### 4.2 启动与链接机制

系统启动由启动代码完成，负责为处理器运行建立基本环境，例如栈空间初始化和 BSS 段清零等。之后，控制流转入主程序入口，开始执行系统级软件逻辑。

链接脚本则负责约束程序在目标地址空间中的布局，使编译结果能够与当前 SoC 的存储组织方式匹配。通过启动代码与链接脚本的配合，软件能够按照处理器系统的要求被正确装载和执行。

### 4.3 异常与中断处理流程

当前工程已经建立了与 CPU 控制能力相对应的异常与中断处理路径。典型流程包括：

1. CPU 检测到异常或中断事件  
2. 进入异常入口代码  
3. 保存必要上下文  
4. 跳转到统一分发逻辑进行处理  
5. 完成必要的软件响应  
6. 返回原执行流继续运行  

这一过程说明当前系统已经不只是支持普通顺序执行，还支持系统级控制流管理。对 CPU-SoC 工程而言，这一能力是从“能执行”走向“能工作”的关键一步。

### 4.4 调试输出支持

为提高 bring-up 和调试效率，当前工程实现了仿真环境下的调试输出支持。软件可以通过轻量接口输出字符、字符串和基础数值信息，仿真平台再将这些信息打印到控制台。

这一机制的意义主要体现在两个方面：

- 提高运行状态的可观察性
- 降低对波形手工排查的依赖

因此，软件部分不仅承担程序执行入口的职责，也承担系统调试辅助的职责。

## 5. 仿真平台设计

### 5.1 仿真平台的整体目标

当前仿真平台的目标不是构造复杂验证环境，而是在工程阶段内提供一个稳定、可复用且便于调试的基础验证平台。其核心目标包括：

- 能够加载软件镜像并启动系统运行
- 能够提供时钟与复位驱动
- 能够观察程序运行结果
- 能够输出调试信息
- 能够辅助判断测试是否通过

因此，当前仿真平台是整个工程软硬件闭环的重要组成部分，而不是单纯的“波形生成工具”。

### 5.2 测试平台的组成方式

当前仿真平台主要由以下几类内容组成：

- 顶层 testbench，用于驱动系统时钟与复位
- 程序加载机制，用于向存储系统提供待执行镜像
- 运行观察逻辑，用于检测仿真结束条件
- 输出监测逻辑，用于打印调试字符
- 波形支持，用于在需要时进行时序级观察

通过这些部分的配合，仿真平台能够完成从“启动 SoC”到“判断执行结果”的整个过程。

### 5.3 程序加载与运行方式

当前工程的软件镜像在软件编译流程中生成，然后由仿真平台在运行前加载到存储系统中。CPU 复位后从既定入口地址开始执行，随后按照程序逻辑完成初始化、主程序运行以及异常/中断处理。

这样的组织方式具备两个优点：

- 软件与硬件路径分离清晰，便于维护
- 仿真运行结果可以与软件编译结果直接对应

因此，程序加载不再是手工硬编码测试，而是已经形成了较为规范的工程流程。

### 5.4 PASS/FAIL 判定机制

当前工程通过仿真控制寄存器建立了明确的运行结果判定方式。测试程序在执行完成后，可以向控制寄存器写入约定值，由 testbench 识别并给出 PASS 或 FAIL 结果。

这种方式比单纯依赖人工波形分析更高效，也更适合后续扩展为基础回归流程。

### 5.5 调试信息输出机制

除了结束判定，当前仿真平台还支持调试字符输出。软件通过写入调试输出寄存器，将字符传递给 testbench；testbench 再根据写事务将字符打印到控制台。

这种机制能够支持连续字符串输出，并且适合用于观察中断进入、异常处理、关键变量值等运行信息，是当前系统 bring-up 阶段非常实用的辅助能力。

### 5.6 Make 与构建流程在仿真平台中的作用

当前工程通过多层 Makefile 将软件编译与仿真运行组织为统一流程。其作用不是替代仿真平台本身，而是把以下过程串接起来：

- 软件编译与链接
- 镜像文件生成
- RTL 编译
- 仿真运行
- 波形查看与结果清理

因此，Make 系统在当前工程中的价值主要体现在“流程组织”和“重复运行效率”上，而不是成为文档主体。它体现的是工程化构建能力，而仿真平台本身仍然是整个验证闭环的主体。

## 6. 工程中的关键约定

### 6.1 地址空间约定

当前工程中与仿真平台直接相关的地址空间约定如下：

| 地址 | 功能 | 说明 |
|---|---|---|
| `0xFFFFFFF0` | 仿真结束控制 | 用于向仿真平台报告程序结束状态 |
| `0xFFFFFFE0` | 调试输出 | 用于将字符信息发送到仿真控制台 |

这些地址是当前 SoC 与 testbench 之间交互的重要接口。

### 6.2 仿真控制约定

当前仿真执行采用明确的控制机制：

- 程序运行结束后通过 MMIO 通知 testbench
- testbench 根据写入值判断执行状态
- 在需要时生成波形文件用于进一步分析

这使得仿真结果不再依赖隐含假设，而是具备明确的观察入口。

### 6.3 调试输出约定

当前调试输出采用“软件写字符，testbench 负责显示”的方式。其特点是：

- 软件侧实现简单
- 仿真侧观察直接
- 适合当前 bring-up 阶段使用

此外，当前工程已经在软件侧建立了基础格式化输出支持，可用于打印字符串、十六进制数和十进制数等常见调试信息。

### 6.4 主要输出文件说明

软件构建与仿真运行过程中，主要输出文件如下：

| 文件 | 作用 |
|---|---|
| `program.elf` | 链接后的可执行文件 |
| `program.bin` | 二进制镜像 |
| `program.hex` | 供仿真加载的十六进制镜像 |
| `program.dis` | 反汇编结果，便于检查指令布局 |
| `simv` | 仿真生成的可执行文件 |
| `waveform.vcd` | 仿真波形文件 |

这些输出文件共同构成了从软件构建到仿真分析的工程产物链路。

当前工程的主要顶层目录如下：

从职责划分来看，当前工程已经形成比较清晰的层次：

这种结构使硬件、软件和仿真之间的关系相对清晰，也便于后续继续扩展。

对于面向数字 IC / RTL / SoC 方向的工程展示而言，这一版本能够体现以下几类能力：

- 基础 CPU-SoC 系统搭建能力
- 异常与中断处理能力
- 底层软件运行支持能力
- 仿真平台与工程流程组织能力
- 软硬件协同 bring-up 能力

因此，这一工程版本已经具备作为 SoC 基础项目说明和后续扩展基础的价值。
